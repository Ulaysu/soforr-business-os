# Module Boundaries

Modules are namespaces/folders inside the existing projects, not separate deployables. Each module owns its data. Other modules use its Application-level queries/interfaces and never write to its tables.

A module may depend only on modules listed under "Depends on". Cycles are forbidden.

The model is deliberately minimal; entities are named for orientation and refined in their backlog items.

---

## Audit
- **Class:** SELLABLE-P0.
- **Responsibility:** An append-only record of business-sensitive actions: who did what, to which record, when, in which request.
- **Concepts:** `AuditEvent` (organization, optional actor, a stable dotted action code such as `membership.role_assigned`, optional entity type and id, optional short description, correlation id, UTC time). The action codes are constants in `AuditActions`; a code never changes meaning once released.
- **Writing:** `IAuditLog.Record(entry)` adds the event to the current unit of work **without saving**, so it commits or fails together with the command that caused it (ADR 0003). The log supplies the id, the time and the request's correlation id; the caller supplies the organization, the actor and the facts. There is no way to read, change or delete an event through it.
- **Reading:** `ListAuditEvents` (Owner only, permission `AuditView`; newest first; optional exact filters by action, entity, actor and time range; page size 1 to 100) and `GET /api/v1/audit-events`. There is no endpoint that creates, changes or deletes an event.
- **Invariants:** Append-only at three levels: the Domain entity has no mutating members, the context refuses to save a changed or deleted event (`AppendOnlyViolationException`), and a database trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` on `AuditEvents` from any source. Tenant-scoped (query filter and write guard). No personal data in an event (no e-mail address, no password); people and records are referred to by id. An event outlives its user: there is deliberately no foreign key from the actor to the user table.
- **Recorded today:** `user.registered`, `membership.role_assigned` (at registration, the Owner role), `auth.sign_in_succeeded`, `auth.account_locked` (once, when the lock starts), `auth.signed_out`. Later items add theirs (inventory adjustments, receipts, sales and voids, role changes).
- **Depends on:** Organizations.

## Organizations
- **Responsibility:** Tenants and their settings.
- **Concepts:** Organization (name, currency, timezone). There is no country attribute; country, currency, time zone and locale are distinct concepts (see [architecture boundaries](architecture.md#future-architecture-boundaries-marketplace-and-country-markets)). Whether and when an organisation country is introduced is an open owner decision.
- **Commands:** UpdateOrganizationSettings (name, time zone and the optional overdue materiality threshold, a non-negative amount in the organization's currency, absent meaning none; the currency cannot change).
- **Queries:** GetOrganization.
- **API:** `GET /api/v1/organizations/{id}` (permission `OrganizationView`: every role) and `PUT /api/v1/organizations/{id}/settings` (`OrganizationManageSettings`: Owner only), documented in OpenAPI. A signed-in user is required; the id must be the caller's own organization, otherwise the answer is 404. There is no create endpoint: an organization is created by registering (Identity).
- **Invariants:** Every tenant-owned record in any module references exactly one organization. The name is required (at most 200 characters, trimmed); the time zone is an IANA identifier supported by the application's runtime time zone database; the currency is one of Soforr's supported ISO 4217 currencies (a maintained snapshot of the current set) and is fixed at creation, so it is never silently changed once transactions exist; timestamps are UTC.
- **Depends on:** none.
- **Tenant context:** `IOrganizationContext` (Application) exposes the current organization id, derived on the server from the authenticated membership (a claim written at sign-in from the stored membership) and never from request data; null means no organization and consumers fail closed. It feeds the query filters and the write guard in `AppDbContext` (IDENTITY-003).

## Identity
- **Responsibility:** Who is calling and which organization and role they act with ([ADR 0002](../decisions/0002-authentication.md)).
- **Concepts:** Membership (user, organization, role; Domain) and Role (Owner, Manager, Staff). The credential record (`ApplicationUser`: password hash, lockout, security stamp) is ASP.NET Core Identity's and lives only in Infrastructure.
- **Commands:** Register (creates the user, a new organization and the Owner membership in one transaction), SignIn.
- **Queries:** GetCurrentUser.
- **Ports (Application):** `ICurrentUser` (user id, organization id, role; null when not authenticated), `IUserAccounts` (stage a validated, hashed user without saving), `ISessionService` (start and end the cookie session).
- **Authorization (IDENTITY-002):** `Permission` and `RolePermissions` (fixed role matrix in code, see [security.md](../security/security.md)); handlers call `ICurrentUser.Require(permission)` first.
- **API (IDENTITY-001):** `GET /api/v1/auth/antiforgery`, `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me`. Mapped **only in Development** until e-mail verification (IDENTITY-004) and rate limiting (SECURITY-002) exist.
- **Planned (see [backlog.md](../product/backlog.md), not all implemented):** commands AssignRole and DeactivateUser, queries ListMembers and GetEffectivePermissions, and the invariants email unique, passwords never stored in plain text, and one role per membership.
- **Invariants:** one membership per user (unique index); a membership has a known role; the registering user is the Owner. "An organization always keeps at least one Owner" is enforced when member management exists (IDENTITY-002). Permissions per role arrive with IDENTITY-002.
- **Depends on:** Organizations.

## Catalog
- **Responsibility:** What the business buys and sells.
- **Concepts:** Product (SKU, name, unit of measure, selling price, cost price, optional reorder settings, active flag), owned by exactly one organization. Reorder settings are a reorder point (a non-negative `Quantity`) and a lead time in days.
- **Commands:** CreateProduct, UpdateProduct, DeactivateProduct.
- **Queries:** GetProduct, SearchProducts.
- **Invariants:** SKU, name and unit of measure are required (trimmed; at most 64, 200 and 32 characters); prices are ≥ 0 and in the same currency; reorder point ≥ 0 and lead time ≥ 0 days; a product with history is deactivated, never hard-deleted (the Domain offers no delete). The `Product` entity enforces these. Cost price is required and zero is a valid stored cost; there is no "unknown cost" state, because no requirement establishes one. Two rules need more than one entity and are enforced elsewhere, not yet implemented: SKU unique within the organization, compared case-insensitively with the entered casing preserved ([ADR 0006](../decisions/0006-sku-uniqueness.md)), which the database must enforce and the handlers report as a conflict; and prices in the organization's currency (checked by the handlers, which know the organization).
- **Commands (CATALOG-003):** CreateProduct, UpdateProduct (replaces the details, including the SKU), DeactivateProduct (idempotent). **Queries:** GetProduct, SearchProducts (paginated: page size 1 to 100, default 25; text matches part of the SKU or name without regard to case; inactive products only on request).
- **API:** `POST /api/v1/products` (201 + `Location`), `GET /api/v1/products?q=&includeInactive=&page=&pageSize=`, `GET /api/v1/products/{id}`, `PUT /api/v1/products/{id}`, `POST /api/v1/products/{id}/deactivate`, documented in OpenAPI. There is no delete and no reactivate (products are never deleted; reactivation is an open question). Permissions: see the matrix in [security.md](../security/security.md). Another organization's product is a 404.
- **Rules in the handlers:** prices are amounts in the **organization's currency** (the request has no currency, so a product cannot be priced in another one); selling and cost price are required (a zero cost is entered as 0); reorder point and lead time are both given or both omitted; a duplicate SKU in any letter case is `409 product.sku_taken`, first by a check and then, if two requests race, by the unique index (ADR 0006); the cost price is `null` for callers without `ProductViewCost`.
- **Future considerations (decided not to build now):** (1) **Reactivation** of a product is a lifecycle decision still to be made: whether it returns to normal search, SKU preservation (it keeps its SKU today), pricing validity, existing stock, audit. Until then a deactivated product can be updated but not reactivated, and keeps its SKU reserved until an authorized update changes it. (2) **Concurrent edits** of one product are last-write-wins; product-level optimistic concurrency is not introduced and can be added if it becomes a problem. (3) **Audit history** of changes to the SKU, prices and activation is business-sensitive and belongs to the audit work (AUDIT-001 and after). (4) `ProductViewCost` is the one permission for everything cost-derived (cost price now; later cost of goods, margins, stock valuation): new cost-derived output must use it.
- **Persistence (CATALOG-002):** table `Products`, tenant query filter, per-organization case-insensitive unique SKU enforced by the database (ADR 0006), CHECK constraints. The Domain is unchanged. No handlers or endpoints yet (CATALOG-003).
- **Depends on:** Organizations.

## Inventory
- **Responsibility:** Stock quantities, derived from movements.
- **Concepts:** InventoryMovement (append-only: product, signed non-zero quantity delta, reason, source type and source id, actor, optional note, UTC time) and StockLevel (current non-negative quantity of one product in one organization, changed only by applying a movement, maintained transactionally with the movements). Reasons in the MVP: PurchaseReceived, SaleCompleted, ManualAdjustment, Return, Damage; Transfer arrives with multiple stock locations.
- **Commands:** AdjustInventory (INVENTORY-003; manual, reason `ManualAdjustment`, a note is required); RecordMovement (internal, `StockMovementRecorder`, called by Purchasing/Sales handlers and by AdjustInventory).
- **Queries (INVENTORY-003):** GetStockLevel, ListLowStock, GetMovementHistory.
- **API (INVENTORY-003):** `POST /api/v1/inventory/adjustments` (201 with the movement id and the new quantity; 200 with `alreadyRecorded` true when the optional client-chosen `adjustmentId` was already recorded; removing more than exists is 422 `stock_level.insufficient_stock`; a conflict that outlasts three attempts is 409), `GET /api/v1/inventory/stock/{productId}`, `GET /api/v1/inventory/low-stock`, `GET /api/v1/inventory/stock/{productId}/movements`. Permissions: see the matrix in [security.md](../security/security.md). Stock changes only through recorded movements: there is no endpoint that sets a quantity, and none that changes or deletes a movement.
- **Every adjustment is traceable:** it writes the movement and an `inventory.stock_adjusted` audit event in **one transaction** (the event is staged by the recorder's `onStaged` hook on every retry attempt, so a conflict-and-retry still yields exactly one of each, and an idempotent repeat adds none). The event states the signed change, never the note.
- **Low stock (one definition, `LowStock.IsLow`):** an **active** product with reorder settings whose stock is **at or below** its reorder point; a product that has never had stock counts as 0. The stock level's `isLow` and the low-stock list can never disagree. The list is the emptiest first, then by name. The comparison is made in memory over the organization's active products that have reorder settings (a stock quantity is a value object the database cannot compare); that set is small for the target business and a database-side comparison can replace it if a customer outgrows it.
- **Reading the ledger needs its own permission** (`InventoryViewHistory`: Owner and Manager), because the history shows who changed stock and why.
- **Persistence and recording (INVENTORY-002):** tables `StockLevels` and `InventoryMovements`; `StockMovementRecorder` (Application) writes a movement and updates the stock level in one transaction with optimistic concurrency, bounded retry that re-validates, and idempotency (see [ADR 0004](../decisions/0004-inventory-concurrency.md)). Insufficient stock is a rule violation (422, `stock_level.insufficient_stock`); a conflict that outlasts three attempts is `409 inventory.concurrency_conflict`. No endpoints yet: INVENTORY-003 adds adjustments and queries with their permissions.
- **Queries:** GetStockLevel, ListLowStock, GetMovementHistory.
- **Invariants:** Every change has a reason and a movement; movements are immutable, with no setters and no mutating methods (corrections are new movements); a manual adjustment requires a note; stock level equals the sum of movements; stock cannot go negative by default, and a movement that would make it negative is rejected and changes nothing; updates are concurrency-safe. The Domain enforces everything above except concurrency-safety and "the same source cannot record the same movement twice", which need the database (ADR 0004, INVENTORY-002). The reason fixes the sign of a movement: `PurchaseReceived` and `Return` add stock (positive), `SaleCompleted` and `Damage` remove stock (negative), and `ManualAdjustment` may be either, because an adjustment can discover an excess or a shortage; a movement whose sign does not match its reason is rejected by the Domain.
- **Depends on:** Catalog, Organizations.

## Purchasing
- **Responsibility:** Buying stock from suppliers and receiving it.
- **Concepts:** Supplier (name, optional contact details, active flag), PurchaseOrder (draft → placed → partially received → received / cancelled; an optional free-text reference of at most 100 characters, no generated number yet), PurchaseOrderLine. The Domain and persistence are PURCHASING-001; the commands, queries and API are PURCHASING-002.
- **State machine:** `Draft → Placed → PartiallyReceived → Received`, and `Cancelled` from `Draft` or `Placed` only (nothing may have been received). Lines can be added, changed or removed only in a draft; an order needs at least one line to be placed; receiving is allowed from `Placed` or `PartiallyReceived`, goes to `PartiallyReceived` while any line is outstanding and to `Received` when every line is complete; `Received` and `Cancelled` are final. Every other transition is rejected by the Domain.
- **Lines:** one line per product per order (also a unique index); the ordered quantity is positive and the received quantity is between zero and the ordered quantity; the unit cost is in the order's currency. A receipt is validated completely before any quantity changes, and it cannot receive more than a line's outstanding quantity.
- **Currency ownership:** a purchase order is in the organization's authoritative currency. The Organization module owns that currency (fixed at creation); the Application layer obtains it through `OrganizationCurrency.ResolveAsync` (the single resolver Catalog also uses) when it creates an order and passes it to `PurchaseOrder.CreateDraft`. The Domain only stores it and keeps every line cost in that currency; it never queries Organization persistence. The create command must not carry a currency (a client cannot choose one), and the database has no foreign key for it (structure is the database's job, the cross-module rule is the handler's). `CreatePurchaseOrder` implements this (the request has no currency field and one in the body is ignored). Multi-currency purchasing is out of scope.
- **Totals:** a line total is `unit cost × ordered quantity` (`Money.Multiply`: exact product rounded to 4 decimal places, half away from zero, range-checked); an order total is the sum of its line totals. Totals are computed from the lines and never stored. They are not rounded to a currency's minor unit.
- **Commands:** CreateSupplier, CreatePurchaseOrder (a draft with all its lines at once; editing a draft's lines and deactivating a supplier have no command yet), PlacePurchaseOrder, ReceivePurchase, CancelPurchaseOrder (PURCHASING-002); ApproveReorder (creates a purchase order from a recommendation; later).
- **Queries:** GetPurchaseOrder, ListPurchaseOrders, ListSuppliers.
- **Receiving (PURCHASING-002):** `ReceivePurchase` loads the order, validates the whole receipt in the Domain, stages one `PurchaseReceived` movement per line through `StockMovementRecorder.StageAsync`, adds a `PurchaseReceipt` record (the order, and for each line the line id, product and quantity) and the audit event, and saves once: received quantities, status, movements, stock levels, the receipt record and audit commit together or not at all, so a receipt that did not commit does not reserve its id. The receipt id (optional, client-chosen; generated when absent) is the receipt's key (unique per organization) and the movements' source id (the ADR 0004 idempotency index stays). **A receipt id means exactly one receipt:** the same id with the same order, the same set of lines and the same quantities is a repeat and answers 200 `alreadyRecorded` without changing anything; the same id with anything different (another quantity, another or additional or missing line, another order) is 409 `purchase_order.receipt_id_conflict` and changes nothing. Two requests with the same id arriving together: one commits, the other is retried and then sees the stored receipt (repeat or conflict). The order carries the `xmin` token: a concurrent receipt, cancel or place of the same order makes the later save fail, and the handler re-reads and re-validates (up to three attempts, then 409 `purchase_order.concurrency_conflict`), so a receipt that no longer fits is reported as the rule violation it is. Stock conflicts use the recorder's own retry.
- **API (PURCHASING-002):** `POST /api/v1/purchasing/suppliers`, `GET /api/v1/purchasing/suppliers`, `POST /api/v1/purchasing/orders` (no currency, no totals in the request), `GET /api/v1/purchasing/orders` (status and supplier filters), `GET /api/v1/purchasing/orders/{id}`, `POST /api/v1/purchasing/orders/{id}/place`, `POST /api/v1/purchasing/orders/{id}/cancel`, `POST /api/v1/purchasing/orders/{id}/receipts`. State and quantity rules are 422; another organization's supplier, product or order is 404. Permissions: see [security.md](../security/security.md).
- **Invariants:** Receiving is idempotent per receipt (no double stock); received quantity cannot exceed what the order allows; totals computed by deterministic code; receiving writes Inventory movements in the same transaction.
- **Snapshots:** a purchase order line must record the product's name, SKU and the price at the time, not read them from the product later; the Catalog describes the current state and a purchase describes what happened.
- **Depends on:** Catalog, Inventory, Organizations.

## Sales
- **Responsibility:** Recording sales and their effect on stock.
- **Concepts:** Sale, SaleLine, payment status (recorded only; no payment processing), optional Customer reference. The Domain and persistence are SALES-001; the commands, queries and API are SALES-002.
- **Domain (SALES-001):** `Sale` is recorded already completed (never a draft) with all its lines through `Sale.Complete`, and the only change that can follow is `Void`: `Completed → Voided`, final, with a required reason (at most 500 characters), the voiding user and the time (not before the sale). Lines, prices and totals never change. One line per product per sale (also a unique index). The sale is in one currency (the organization's, passed in by the Application layer, which will obtain it from `OrganizationCurrency.ResolveAsync`); every price and cost on a line must be in it.
- **Line snapshots:** each line stores the product's SKU, name and unit of measure, the **catalog unit price**, the **final unit price** actually charged, the **cost price** and the currency, all as they were at the time of the sale. The quantity is greater than zero; the final price is never negative (zero is allowed, for a free sample).
- **Price override rule (data model only; the permission and limits are SALES-004):** the final price equals the catalog price unless the line was overridden or discounted; a price that differs from the catalog price (lower or higher) **requires a reason**, and a reason is accepted only for a differing price (at most 200 characters), in the Domain and as a CHECK constraint. The user who recorded the sale (`CreatedByUserId`) is accountable for any override on it. The discount of a line is derived (`catalog price × quantity − line total`), never stored.
- **Totals:** a line total is `final unit price × quantity` (`Money.Multiply`, the same rounding policy as purchasing); the sale total is the sum of line totals; the cost total (`cost price × quantity` summed) and the total discount are derived the same way. Totals are computed from the lines and never stored; a total that would not fit the stored precision is refused before the sale exists.
- **Sales on account (CUSTOMER-002, part 1):** a sale may carry a `CustomerId`. The product owner's decisions: (1) only a sale **with a customer** can be left unpaid or part-paid; a **walk-in sale is always paid in full** at the time of sale, has no due date and no balance (a stated amount must equal the total); (2) `CreateSale` takes an optional `amountPaid` (0 up to the total) and a free-text `paymentMethod`, and records the payment in the same transaction as the sale and the stock movements; an **absent amount means paid in full**, so a debt is never created by leaving something out; (3) an **over-payment is refused**, never recorded as credit, so a balance can never go negative; (4) the **due date is fixed when the sale is recorded** (sale date plus the customer's credit terms, or immediately when the customer has none, so no organization setting is needed yet) and does not move if the terms change later. The customer must exist in the organization and be active (inactive: 422 `sale.customer_inactive`). A repeated `saleId` is a repeat only if it also asks for the same customer and the same amount paid at the time (`HasSameSettlementAs`; the original payment is compared, not the balance now); anything else is 409 `sale.id_conflict`.
- **Payments (CUSTOMER-002):** `SalePayment` records are **append-only** (the data context refuses to change or delete one, and so a sale line): a payment, or a reversal that points at the payment it takes back in full (a reversal needs a reason; a payment can be reversed once; a reversal cannot be reversed). The payment taken with the sale has the sale's own id. Money is recorded, never processed. The **amount paid** is derived (payments minus reversals) and the **outstanding** balance is `total − amount paid` for a completed sale on account (zero for a walk-in or a voided sale), so both can be reproduced from the records and are never edited. `PaymentRevision` changes with every payment event, so the sale's concurrency token stops two payments recorded together from paying more than is owed. A **sale with money on it cannot be voided** (422 `sale.has_payments`) until its payments are reversed. Recording and reversing later payments, and the customer balance, are described next.
- **RecordPayment / ReversePayment (CUSTOMER-002, part 2):** `POST /api/v1/sales/{id}/payments` and `POST /api/v1/sales/{id}/payments/{paymentId}/reverse`. The sale's aggregate enforces the rules (see above); the handler adds the audit event (`sales.payment_recorded` states the amount, never the method or the customer; `sales.payment_reversed` never carries the reason) and saves in one transaction. A payment's date `paidAtUtc` (default now) is when the money was received: not before the sale, not in the future; it is kept to microseconds, as the database stores it, so a genuine retry is never mistaken for a different payment. **Idempotency by a client-chosen id** (the payment's or the reversal's key is unique per organization): the same id for exactly the same payment (same sale, amount, method, and the same date when one is given) answers 200 `alreadyRecorded` and changes nothing, even after the sale is fully paid; the same id for anything different is 409 `sale.payment_id_conflict`; a refused payment does not reserve its id. **Concurrency:** the sale's `xmin` token (moved by `PaymentRevision`) stops two payments recorded together from saving together; the loser is retried up to three times, re-reading and re-validating, so a payment that no longer fits is the rule violation 422 `sale.payment_exceeds_outstanding`, never recorded on top; after three attempts it is 409 `sale.concurrency_conflict`. Permissions: `PaymentsRecord` (Owner, Manager and Staff: a cashier takes payments) and `PaymentsReverse` (Owner and Manager).
- **GetCustomerBalance (CUSTOMER-002, part 2):** `GET /api/v1/customers/{id}/balance` (permission `SalesView`, so a cashier can see what a customer owes). For the customer's **completed** sales on account it returns the total outstanding (each sale's total minus its payments net of reversals, summed), the overdue part (sales whose due date is **strictly before** the evaluation time; day-by-day aging buckets and the organization's time zone belong to INTEL-005), the counts and the open sales, earliest due first. It is derived from the sales and payment records on every request and never stored, so it reconciles to the last decimal with a raw SQL sum of the records (tested). Voided sales, walk-in sales and other customers' sales are not counted; an inactive customer's balance can still be read; another organization's customer is 404.
- **Concurrency:** the sale carries the `xmin` token (ADR 0004), so two people voiding the same sale at once cannot both save. A sale and its lines are never deleted (foreign keys are `Restrict`). The sale's key is (organization, sale id), because the id may be chosen by the client.
- **CreateSale (SALES-002):** takes products and quantities, and optionally a final `unitPrice` with a `priceReason` per line (SALES-004, below); without a price the line is charged the catalog price read by the server at that moment (a client currency or total is never read). In one transaction it stages one `SaleCompleted` movement per line through `StockMovementRecorder.StageAsync` (a line that would take more than exists is 422 `stock_level.insufficient_stock` and nothing is saved), adds the sale with its snapshots and the audit event, and saves once: sale, movements, stock levels and audit commit together or not at all. The optional client `saleId` is the sale's key and the movements' source id: the same id asking for exactly the same products and quantities is a repeat (200 `alreadyRecorded`, nothing changes, even if a catalog price changed meanwhile); the same id with anything different is 409 `sale.id_conflict`; a sale that did not commit does not reserve its id; ids are unique per organization. Concurrent sales of the same stock are decided by the stock level's concurrency token with the recorder's bounded retry, each attempt re-reading and re-validating, so of two sales of the last unit exactly one succeeds.
- **Price overrides (SALES-004):** the product owner's decisions: (1) **who:** stating a price on a line needs `SalesOverridePrice` (Owner and Manager; a Staff cashier sells at the catalog price and is refused with 403 even if the price equals the catalog price); (2) **limit:** the price can never be below zero, and a price **below the product's recorded cost price** additionally needs `SalesSellBelowCost` (Owner only), otherwise 403 `sale.line_price_below_cost` (the message does not reveal the cost); a price equal to the cost is allowed; (3) **request:** the client states the **final unit price**, never a discount percentage; the discount is derived (catalog price minus price charged, per line and in `totalDiscount`; a price above the catalog gives a negative discount). A price that differs from the catalog price needs a reason (at most 200 characters, trimmed), and a reason without a different price, or without a price at all, is refused. Recorded on the line: the catalog price, the price charged, the reason and the cost price; the sale records the user. Totals are computed by the server. Margin intelligence already uses the price charged (the line total). A price override writes a second audit event `sales.sale_price_overridden` (entity: the sale) with the number of overridden lines, the catalog-minus-charged total and the number of lines below cost, never the reason text. All checks that need only the request and the role run before anything is looked up, so a refused request reserves no sale id. A repeat of a sale id is the same sale only if it asks for the same prices and reasons as well (a line stated at the catalog price matches a line charged the catalog price); anything different is 409.
- **VoidSale (SALES-002):** `Owner`/`Manager` only. In one transaction it marks the sale voided (required reason, user, time), stages one `Return` movement per line (source: the sale, so it can never collide with the sale's own `SaleCompleted` movements) and records the audit event (the reason text is never written to the audit trail). A sale can be voided once: a second or concurrent void is refused (422 `sale.not_voidable`), so the stock is returned exactly once.
- **API (SALES-002):** `POST /api/v1/sales`, `GET /api/v1/sales` (status filter), `GET /api/v1/sales/{id}`, `POST /api/v1/sales/{id}/void`. There is no endpoint that edits or deletes a sale. Another organization's sale or product is 404. Cost prices (`costPrice`, `lineCost`, `totalCost`) are returned only to callers with `ProductViewCost`. Permissions: see [security.md](../security/security.md).
- **Commands:** CreateSale, VoidSale, RecordReturn (after Sellable V1).
- **Queries:** GetSale, ListSales, GetSalesSummary.
- **Invariants:** Prices and totals computed server-side; completing a sale writes Inventory movements atomically; a completed sale is never edited, only voided/returned via new records.
- **Snapshots:** a sale line must record the product's name and SKU, the unit price, the cost price and the currency at the time of the sale (and not refer to the product's current values), because products stay editable, including inactive ones. Margin reporting reads the snapshot and requires `ProductViewCost`.
- **Depends on:** Catalog, Inventory, Customers (optional reference), Organizations.

## Offline synchronization (OFFLINE-001)
- **Class:** SELLABLE-P0 (ADR 0007, ADR 0008). Server side only; the client is OFFLINE-002 onward.
- **Responsibility:** Make replay of sales and payments after an outage correct and safe: the server-established authorization of an offline event time, and the replay-safe contract of the existing commands.
- **Concepts:** `OfflineGrant` (an identifier, not a secret; one active per user), `OfflineContact` (append-only server observation), `OfflineEventTimePolicy` (the pure rule), silent gap, offline window.
- **Commands:** IssueOfflineGrant, RecordOfflineContact. `CreateSale` and `RecordPayment` accept an optional offline grant and event time and judge them through `OfflineEventTimeValidator` before anything is looked up or staged.
- **API:** `POST /api/v1/offline/grants`, `POST /api/v1/offline/grants/{id}/contact`; `occurredAtUtc`, `offlineGrantId` and `catalogPriceShown` on `POST /api/v1/sales`; `paidAtUtc` and `offlineGrantId` on `POST /api/v1/sales/{id}/payments`.
- **Invariants:** an offline event time is accepted only inside a silent gap the server observed on the caller's own grant, within 72 hours of the gap start, never in the future, never replaced by server time; a refusal records nothing and reserves no id; a changed catalog price is a conflict, an override is not drift; replays are idempotent (the sale id and the payment id); grants and contacts are tenant-scoped and contacts are append-only.
- **Contract:** [offline-sync-contract.md](../engineering/offline-sync-contract.md).

## Customers
- **Class:** SELLABLE-P0 (accepted V1 product decision, see [sellable-v1.md](../product/sellable-v1.md#accepted-v1-product-decisions); customer balances feed customer intelligence).
- **Responsibility:** Who the business sells to, and what they owe.
- **Concepts:** Customer (name, contact details, optional credit terms), Payment (recorded against a sale; recording only, never processed). `Customer` exists with its persistence and API (CUSTOMER-001); payments, credit sales and balances are CUSTOMER-002.
- **Customer (CUSTOMER-001):** name (required, at most 200 characters), contact details (one optional free-text field, at most 500 characters: personal data is minimized), optional credit terms in days (0 to 365; 0 means due immediately; absent means the organization's default, which belongs to the balance rules of CUSTOMER-002 and INTEL-005), active flag, UTC timestamps. Two customers may share a name. A customer is **never deleted**: it is deactivated, so past sales keep a valid customer; deactivating an inactive customer changes nothing, and a deactivated customer can still be updated. The database keys it by id with an (id, organization) key so sales can reference it together with the organization.
- **Customer API (CUSTOMER-001):** `POST /api/v1/customers`, `GET /api/v1/customers?q=&includeInactive=&page=&pageSize=` (name search without regard to case, ordered by name, page size 1 to 100; contact details are never searched), `GET /api/v1/customers/{id}`, `PUT /api/v1/customers/{id}` (replaces name, contact and terms; absent contact or terms clears it), `POST /api/v1/customers/{id}/deactivate`. There is no delete. `CustomerView` (Owner, Manager, Staff) reads; `CustomerManage` (Owner, Manager) creates, updates and deactivates **and is the only permission that sees contact details** (a cashier needs the name and the terms, not the phone number). Every change is audited (`customers.customer_created`, `customers.customer_updated`, `customers.customer_deactivated`) with a description that never carries personal data.
- **Commands:** CreateCustomer, UpdateCustomer, DeactivateCustomer, RecordPayment (and its reversal by a new record).
- **Queries:** GetCustomer, SearchCustomers, GetCustomerBalance (derived: sales minus payments).
- **Invariants:** Belongs to one organization; personal data minimized; customers with sales are deactivated, not deleted.
- **Depends on:** Organizations. Sales references Customers (not the reverse); customer activity is exposed by a Sales query consumed by Reporting/Intelligence.

## Intelligence
- **Class:** the deterministic part is **SELLABLE-P0**; statistical and AI-assisted parts are FUTURE ([sellable-v1.md](../product/sellable-v1.md)).
- **Responsibility:** Understanding activity with explicit rules and calculations: inventory risk, sales comparisons, margins, purchasing cost changes, customer balance and aging, and the single "things that need your attention" view.
- **Concepts:** `Insight` (type, severity, subject, named facts, reason, recommended action), rules and calculators (pure functions over typed inputs, explicit thresholds and the clock). Later, PRODUCT-P1: `ReorderRecommendation` records with owner approval.
- **Commands:** none in V1 (insights are computed, not stored). Later: `GenerateReorderRecommendations`, `DismissRecommendation`; approval invokes `Purchasing.ApproveReorder` and Intelligence itself never writes purchases or stock.
- **Built (INTEL-001):** the foundation in `Soforr.Application/Intelligence`: `Insight`, `IInsightSource` (found by assembly scan), the `GetInsights` query (permission `InsightsView`, fixed ordering, cost sources run only for callers with `ProductViewCost`, nothing stored) and, from INTEL-002, the inventory risk rule below. Conventions for formulas, periods, thresholds and tests: [intelligence.md](../engineering/intelligence.md). There is no HTTP endpoint yet (INTEL-007).
- **Inventory risk (INTEL-002):** `InventoryRiskRule` over `InventoryRiskInsightSource`. *Window:* the 30 complete local calendar days before today in the organization's time zone (half-open); only **completed** sales count (a voided sale is not a sale). *Formulas:* average daily sales `A = Q ÷ 30` (Q = quantity sold in the window); stock coverage in days `= stock ÷ A` when `Q > 0`, and with no sales in the window there is no coverage ("no recent sales", never infinity); suggested order quantity `= max(0, reorder point + A × lead time − stock)`, rounded to 4 places half away from zero, given only when the product has a reorder point and a lead time (never computed from a missing input) and omitted when it is 0. *At most one insight per product:* `inventory.reorder_point_reached` when the product is low (the one definition shared with the stock level and the low-stock list); otherwise `inventory.runs_out_before_restock` when it has sales and a lead time and coverage is shorter than the lead time. *Severity:* High when there is no stock or coverage is shorter than the lead time; Medium when the reorder point is reached but coverage outlasts the lead time or there are no recent sales. *Edge cases:* a product that never had stock counts as 0; inactive products and products without reorder settings never appear; no history or zero velocity gives no coverage and no run-out insight; zero stock with sales has 0 days of coverage. Facts show coverage to 1 decimal and average daily sales to 2 (half away from zero) and comparisons use the unrounded values. Every insight names the product, its stock, the reorder point, the lead time, the quantity sold, the average and the window it used.
- **Sales metrics (INTEL-003):** `SalesMetricsCalculator` (pure), fed by `SalesMetricsGatherer`; exposed by the `GetSalesSummary` query and by `SalesInsightSource`. *Periods:* the current period is the N complete local calendar days before today (default 30, at most 92) in the organization's time zone; the previous period is the N days immediately before it; both half-open `[start, end)`. A sale belongs to the period containing its time. *Exclusions:* only **completed** sales count; a voided sale counts in neither period. *Formulas:* revenue of a period = the sum of the sale-line totals the Domain computed (final unit price × quantity, rounded per line, so it reconciles to the last decimal with the stored sales and is checked against a raw SQL sum); sale count = distinct sales; revenue growth = `(current − previous) ÷ previous × 100`, to 1 decimal place half away from zero, and when previous revenue is 0 there is no figure (`growthStatus` `no_comparable_previous_sales`), never 0 or infinity. Quantity is reported **per product** and never summed across products (a bag and a kilogram are not comparable). *Top sellers:* ordered by quantity sold in the current period (most first), then revenue, then name, then id; only products that sold something. *Declining:* sales in both periods and quantity fell by at least 20% (`current ≤ 80% of previous`), largest decline first. *Slow movers:* of the active products created before the current period began (so they had the whole period to sell), ordered by current quantity (least first; no sales = 0), then name, then id, the bottom `max(1, floor(n × 20%))`; with fewer than 5 qualifying products the whole ordered list is shown. *Attention list:* `sales.declining_product` and `sales.slow_mover` insights, severity Low, over 30 days against the 30 before; slow-mover insights appear only when at least 5 products qualify (below that the summary lists them all, but flagging every product of a very small shop as slow would be noise). Needs `InsightsView` (Owner and Manager). Lines are summed in memory (a quantity is a value object the database cannot sum, and totals are rounded line by line), which is why the period length is bounded.
- **Margins (INTEL-004):** `MarginCalculator` (pure), fed by the same `SalesMetricsGatherer`; exposed by `GetMarginSummary` and `MarginInsightSource`. *Periods and exclusions* are those of the sales metrics above (whole local days in the organization's time zone, previous period of equal length, completed sales only). *Formulas:* a **management margin, not accounting COGS** (no FIFO, weighted-average costing or inventory valuation): gross margin = revenue (the final price charged) − cost, where cost is the **cost price recorded on the sale line at the time of the sale**, never the product's current cost; margin percentage = gross margin ÷ revenue × 100, to 1 decimal place half away from zero, when revenue is not zero (otherwise there is none); the change is in **percentage points**, current minus previous margin percentage, computed from the unrounded values, and only when both periods have a margin percentage. Average unit price and cost (revenue ÷ quantity, cost ÷ quantity, 4 decimals) are returned for both periods so an explanation can show previous and current price, cost and both margins. *Missing data is never guessed:* the catalog cannot say "unknown cost" and 0 is the only way to leave cost untracked, so a sale line recorded with a cost price of 0 has **no recorded cost**; it is left out of the margin (so it cannot flatter it as pure profit) and reported as revenue without cost, a period with sales but no costed line has no margin (`cost_not_recorded`), a period with partly costed sales is `partly_costed`, and a period with no sales is `no_sales`. *Attention list:* `margin.negative_margin` (High: the costed sales of the current period cost more than they brought in) and `margin.margin_decline` (Medium: the margin percentage fell by at least 5 percentage points, with a margin in both periods; the only threshold, `MarginCalculator.DeclineThresholdPoints`), at most one per product, a loss taking precedence; each shows previous and current price, cost and margin. *Visibility:* the margin reveals costs, so `GetMarginSummary` needs `InsightsView` **and** `ProductViewCost`, and the source declares `RequiresProductViewCost` so the attention list runs it only for callers who hold it.
- **API (INTEL-004):** `GET /api/v1/intelligence/margins?days=&top=` (periods, totals, the top products by gross margin, products at a loss, products whose margin fell, and products with no recorded cost; 400 for an out-of-range `days` or `top`).
- **Receivables (INTEL-005):** `ReceivablesCalculator` (pure), fed by `ReceivablesGatherer`; exposed by `GetReceivables` and `ReceivablesInsightSource`. *Which sales:* completed sales made on account (a customer and a due date) whose derived balance (`Sale.Outstanding`, lines minus payments plus reversals) is above zero; walk-in and voided sales are never receivables. *Payment rule:* a payment is recorded against one sale and reduces that sale only; a reversal restores that same sale, so a customer's balance is the sum of what each sale still owes and no payment is ever re-applied to another sale. *Overdue:* a sale is overdue when its fixed due instant is strictly before now (a sale due exactly now is not yet due). *Days past due* are whole calendar days in the organization's time zone, today's local date minus the due date's local date (at least 0; a sale that fell due earlier today is overdue at 0 days). *Buckets* by days past due: 0-30, 31-60, 61-90, 91+; the buckets of a customer add up to the customer's overdue amount. *Insight* `customers.overdue_balance` (action `collect_payment`): one per customer whose overdue amount reaches the organization's **materiality threshold** (every overdue balance when none is set; compared against the customer's whole overdue amount, not each sale); severity High when any amount is 91+ days past due, Medium when the oldest is 31-90, otherwise Low; facts: overdue, outstanding and not-yet-due amounts, overdue sale count, oldest days past due, the four buckets, the threshold, the as-of date and the oldest five overdue sales (id, amount owed, due date, days past due) with a count of any not listed. Customers are ordered by overdue amount, then outstanding, then name, then id; the insights by severity, then overdue amount, then name. Needs `InsightsView` only: money owed to the business is not a cost price. Nothing is stored; the balances are recomputed from the sales and payments.
- **Purchase cost (INTEL-006):** `PurchaseCostCalculator` (pure), fed by `PurchaseCostGatherer`; exposed by `GetPurchaseCosts` and `PurchaseCostInsightSource`. *What a purchase is:* a line of a **placed** purchase order (placed, partly received or received; drafts and cancelled orders are not purchases), dated when the order was placed and costed at the line's unit cost; the history is the last 365 days. A unit cost of 0 means no cost was recorded: such purchases are left out of every comparison and counted separately. *Change:* per product and supplier, the latest costed purchase against the immediately previous one from the **same** supplier: change % = (latest − previous) ÷ previous × 100, to 1 decimal place half away from zero. A change is **notable** when it is at least **10%** of the previous cost, in either direction, decided on the exact values (a change that rounds to 10.0 but is below 10% is not notable). One costed purchase is reported as insufficient history, never as no change. *Supplier gap:* with two or more suppliers that have a costed purchase, (most expensive latest cost − cheapest latest cost) ÷ cheapest × 100, notable at the same 10%. *Volume:* orders, quantity and spend of the lines placed in the last N complete local days (the report's `days`, default 30). Ties on the placed time are broken by order id. *Insights* (only for purchases in the last 30 complete local days and today): `purchasing.cost_change` (one per product; Medium if any notable change is an increase, Info if all are decreases; names each supplier with both costs and dates) and `purchasing.supplier_cost_gap` (Low; names the cheapest and the most expensive supplier). Cost data: the report and the source need `ProductViewCost` as well as `InsightsView`. Nothing is stored.
- **API (INTEL-006):** `GET /api/v1/intelligence/purchase-costs?days=&top=` (period, volume, the top products by spend with their supplier costs and gap, and every product with a notable supplier change; 400 for an out-of-range `days` or `top`).
- **API (INTEL-005):** `GET /api/v1/intelligence/receivables?top=` (as-of time, totals, buckets, the number of customers with a balance and overdue, and the top customers (default 25, at most 100) with their overdue sales; the totals cover every customer; 400 for an out-of-range `top`).
- **API (INTEL-003):** `GET /api/v1/intelligence/sales-summary?days=&top=` (periods, totals with growth, top sellers, slow movers, declining products; 400 for an out-of-range `days` or `top`).
- **Queries:** GetInsights (the attention list), GetSalesSummary, per-topic metrics (stock coverage, sales comparison, margin, purchase cost, customer aging); later the AI tools wrap these same queries.
- **Invariants:** Deterministic and reproducible from the data and the clock; every insight shows its facts and reason; formulas, comparison periods and thresholds are documented and tested; insights are derived and never override a transaction; tenant-scoped and permission-checked; cost-derived insights need `ProductViewCost`; no model output anywhere in V1.
- **Depends on:** Inventory, Sales, Purchasing, Catalog, Customers (read-only). See [architecture.md](architecture.md#deterministic-intelligence) and [ai-architecture.md](ai-architecture.md).
